# Public read/query layer

Read routes and server functions are read-only. They never migrate, ingest, enrich or contact public sources/OpenAI/xKiro. Turso configuration and clients live in server-only modules. Public DTOs omit credentials, database URLs, source IDs, content hashes, duplicate text fields, internal batch/topic IDs, classification payloads and raw error messages.

Public evidence includes the allowlisted actual `enrichmentProvider` (nullable for legacy/manual fixtures); dashboard enrichment metadata includes selected/actual providers and this run's AI/heuristic/error/fallback counters. A selected provider is not a claim that it processed evidence. Historical mock provenance stays marked as mock; new API failures identify heuristic fallback. No API keys, model payloads or provider exceptions are returned.

## Queries and windows

`GET /api/pulse?window=2h|6h|24h&category=Mobility&source=gdelt` defaults to `2h`. Categories accept the semantic taxonomy (`civic`, `traffic`, `technology`, `business`, `culture`, `food`, `events`, `weather`, `sports`, `other`) or the original editorial buckets for compatibility; sources are `gdelt`, `bluesky`, `hackernews`. Unknown, repeated and invalid query parameters receive 400. Parameters are validated before reads; SQL values are bound parameters.

The window selects topics with at least two distinct signals in that period, filters the source stream and aggregates neighborhood activity. A source filter selects topics with evidence from that provider in the selected window. Scores, growth, confidence and lifecycle always use the fixed all-provider v2 two-hour engine. Filtering never recomputes a one-provider score or rewards unavailable providers. Six/24-hour views can include COOLING topics with a zero current score. Responses expose `activityCount`, a validated `semanticCategory`, an explicitly mentioned `neighborhood` (nullable), and an explicit `scoringWindow: "2h"`. Semantic filters apply consistently to topics, evidence and hotspots; classification comes from persisted topic enrichment metadata, with a conservative legacy fallback.

The dashboard returns bounded `topTopics`, `risingTopics` (HOT/RISING/EMERGING), `snapshot` metadata, a latest-first `sourceStream`, `lastSuccessfulIngestion` and `availableSources`. The home page and browser refresh validate this public model; the internal `trends`/raw-evidence model remains on the server. Excerpts are bounded to 600 characters; stream/topic evidence is limited to 30 signals. Dashboard topic lists are limited to 50. Counts remain complete and truncation is explicit. `GET /api/topics` additionally supports `q`, `lifecycle` and `limit` (1–100), filtering the full topic set before limiting.

`GET /api/topics/[slug]` finds retained canonical topics, including inactive ones. It returns the current topic metrics, summary, Pulse Score, growth, confidence, lifecycle, 24-hour activity, up to 96 recent versioned scoring snapshots within 30 days, source evidence and up to 12 related signals. Related signals belong to another topic sharing category or an explicitly mentioned neighborhood; they are context, not claimed equivalent events. Missing topics return 404; invalid slugs return 400.

Topic detail also includes strict `locationEvidence`: nullable curated neighborhood, support status (`supported`, `mixed`, `insufficient`, `unknown`), dominant-neighborhood mention count, total located signal count and distinct supporting provider count. It derives from the full deduplicated 24-hour topic evidence before display truncation. Support requires two mentions, two providers and a 60% majority among located signals. Related signals use the semantic category; the coarse `other` category alone does not establish a relationship. See [Topic brief](topic-detail.md).

`GET /api/hotspots` accepts the same window/category/source filters. It returns neighborhood mention activity, coordinates at neighborhood centers, average/top Pulse Score and the top topic. Completed, relevant canonical evidence contributes even when a topic is below the ranking threshold; an isolated mention can appear with its capped NEW score without becoming a ranked trend or HOT. Pending items cannot invent topics/locations. Signals deduplicate before neighborhood aggregation. Average pulse is an unweighted mean over distinct contributing topics; ties use score, velocity and slug. Citywide/unknown locations are omitted.

`GET /api/health` reports application and database status, last ingestion, last successful ingestion, latest per-source statuses and the recent 24-hour collected signal count, including pending and irrelevant items. Successful ingestion means a completed source run or a partial run with accepted evidence; empty successful polls qualify. Availability describes a non-stale successful/partial source poll, not a new upstream network probe. Demo health explicitly uses simulated sources and requires no database. Counts are null when storage is unavailable rather than a fabricated zero.

The About page reads this same validated health projection on the server and presents only three source states and the last successful collection, including its date and IST time. Fresh successful sources are Operational; partial polls, stale records and unavailable sources retain distinct labels. Demo sources say Demo and never claim a successful live collection. An unconfigured installation awaits its first collection; a failed database read reports temporary unavailability. Opening About performs no ingestion, enrichment or upstream source probe. The five-step methodology and prominent experimental-data limitations precede the detailed scoring and coverage notes.

## Consistency, freshness and caching

Live observations, topic assignments, source health and snapshot identity execute in one atomic libSQL read batch. Topic pages reuse that shared state and add one parameterized history query, capped at the parent snapshot capture time and 97 rows (96 displayed plus a truncation sentinel). A later publication cannot attach newer history to an older cached snapshot. This replaces a second full read batch; there are no per-topic database loops. Reads validate persisted records and snapshot mode/capture identity with Zod and explicit guards. Recent collected items plus 14-day relevant completed evidence preserve global dedupe across the 24h boundary; old pending/irrelevant items are not loaded. A 15-second Next.js server cache reduces repeated database work; filters and clock-dependent scoring happen after the cache. Live cache keys use the opaque database identity, known validated topic slugs and the parent capture timestamp, never credentials. React request memoization also shares identical dashboard projections between the layout and page. Unknown slugs do not create cache entries. Health bypasses this cache and probes the database directly. Failed refreshes cannot produce a fabricated successful entry; Next.js can serve a previously validated entry during revalidation failures, so responses expose `cacheAgeSeconds` and `refreshDelayed` (over 30 seconds) and mark delayed reads degraded. SDK errors are replaced by opaque codes before background refresh logging. Read endpoints remain dynamic and send `Cache-Control: no-store`.

Cache arguments additionally contain an opaque SHA-256 identity derived from the database URL, so changing the configured database cannot reuse another database's persisted cache. Neither URLs nor tokens are stored in cache keys. SDK HTTP requests set `cache: no-store` and have an eight-second abort deadline. Caller cancellation is preserved. Retained topic briefs remain readable during complete upstream source failure when the stored snapshot and evidence are valid; their DTO still reports collection `unavailable` and its notice. Unreadable storage or a missing snapshot continues to produce the controlled topic recovery state.

Collection timestamps are preserved. Rankings age using the request clock; collections over 90 minutes old are stale. Data reads return 200 for available degraded/stale evidence with explicit metadata, 503 when storage or live collection is unavailable. Health returns 503 for unconfigured/unavailable storage, missing/stale collection or degraded source coverage. Error responses use fixed public codes; diagnostics log codes without SQL text or credentials. A valid but empty filtered result is 200. Demo uses reproducible fictional observations and never impersonates a successful live ingestion.
# City signal edition contract

`GET /api/pulse` now defaults to `window=now`; explicit `2h`, `6h` and `24h` retain their existing meaning. `requestedWindow` records the selection; `window` and `snapshot.queryWindow` always name the actual evidence window. NOW chooses the shortest window with a qualifying topic, then the shortest with eligible evidence. Source/category filters participate in that choice. The score, source diversity, confidence and lifecycle always come from the unchanged latest-2h deterministic engine. All three candidate windows reuse one engine evaluation. Search remains local to the bounded returned topic list.

Every source now includes `healthState`, `lastAttemptAt`, `lastSuccessAt`, `lastItemAt`, `lastErrorAt`, `lastErrorType`, and `itemsLastRun`. `healthState` is `live`, `delayed`, `degraded`, `stale`, `error`, `unavailable` or `demo`. A successful zero-result poll updates success and remains live. Source health does not depend on selected-window activity, enrichment provider or publication success. Error types are bounded machine codes; raw upstream errors and credentials remain private. `availableSources` includes recently successful live/delayed/degraded sources, even after a later failed poll. `totalSignals` is the deduplicated, relevant, enriched evidence still within 24h at evaluation time, rather than the original snapshot's historical total. It can differ from the source stream, which also includes pending signals.

`GET /api/og/[slug]` is a read-only 1200×630 PNG for topic shares. It shows actual score, 2h evidence counts, lifecycle, evaluation timestamp and demo/stale labeling. Unknown topics return 404 and unavailable reads return 503. Responses use `Cache-Control: no-store`; social platforms may retain their own copies. Topic pages use the stable production canonical for clipboard/Web Share links.

## Recent conversation discovery

The dashboard's additive `recentConversations` array exposes at most eight enriched, relevant topics with deduplicated evidence in the last 24 hours, excluding topics already in the selected ranking. It includes singleton mentions and quieter conversations, ordered by latest evidence timestamp with slug ties. Each entry contains `slug`, `title`, semantic `category`, nullable mentioned `neighborhood`, actual `latestAt`, selected-source `signalCount` and supporting `sources`. It has no popularity score or invented ranking. Source/category filters apply; its evidence window remains explicitly 24H while the ranking window can be 2H or 6H. The local search filters this bounded result as well. Pending, irrelevant, future, expired and missing-snapshot evidence cannot populate the section. The DTO defaults the field to an empty array for compatibility with older validated responses. This adds no database query or ingestion to public reads and does not change scoring.

Live heuristic topics with lowercase keyword labels use a literal, bounded source headline for public display, preserving its original casing and wording while removing URL/hashtag/attribution noise. The earliest retained evidence supplies a stable representative headline. Topic IDs, canonical stored labels, slugs, source timestamps, scores and historical records are unchanged. Demo/curated and API-generated labels retain their supplied titles. A wider-window list with no topic meeting the latest-2H momentum threshold is presented as Recent activity, with the lead labeled Recently observed; its actual current score remains visible.
